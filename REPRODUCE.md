# Reproducing Tortoise v1.0

From a fresh clone to (1) every campaign summary rebuilt from the committed per-run data, (2) a short set of real
SPICE runs that must reproduce recorded outcomes, and (3) re-running any full campaign. Everything here is
simulation; see [`README.md`](README.md) for what the results do and do not show.

Tested on Linux (Ubuntu, x86-64, 4 cores) with ngspice-42, Python 3.13 and numpy 2.5.3.

**What this repository contains and what it does not.** All scripts, the per-run metric JSONs of every campaign run,
all summaries, warm-start and calibration start states, the weights and the dataset are included. The **simulated
waveforms** (`*.csv.gz`, 1 µs resolution), **simulated netlists** (`*.cir.gz`), **Monte Carlo draw files**
(`*_draws.json`) and energy raw files (`*.raw.gz`), about 13 300 files and 780 MB in total, are **not included**.
Nothing in §4 or §5 needs them. They are needed only for waveform-level analysis (the six summary steps listed in §4,
`results/wrapup/scripts/s2_mechanism.py`) and to diff a re-run's waveforms; they are regenerated by re-running the
campaign phases in §6, which write them next to each per-run JSON.

```

```

Every campaign used **ngspice-42** (`ngspice --version`). Another version may change transient results in the last
digits; the smoke test (§5) will show it.

## 2. Clone

```bash
git clone <repository-url> tortoise
```

```bash
cd tortoise
```

No Git LFS is used; a plain clone has everything this repository contains.

## 3. Set up the layout the scripts expect

The design and campaign scripts hard-code `/home/claude/w/...` (the directory layout of the machine the simulations
ran on). They are not refactored; instead a symlink layout is recreated:

```bash
sh tools/setup_layout.sh
```

It creates `/home/claude/w/repo` → the clone, `/home/claude/w/{eval,sim/models,sim/tools}` → `rev10/...`, and
`/home/claude/w/sim/circuits/` with links to `rev10/sim/circuits/*`. All builds and simulations run in directories
under `/home/claude/w/sim/`, never inside the repository. It needs write access to `/home/claude` (create it first if
your account cannot: `sudo mkdir -p /home/claude && sudo chown $USER /home/claude`). Re-running it is safe; it
re-points the links to whichever clone ran it last.

## 4. Rebuild the summaries from the per-run data (no SPICE)

```bash
sh tools/reproduce_summaries.sh
```

What it does ([`tools/reproduce_summaries.sh`](tools/reproduce_summaries.sh)):
1. runs every committed summary script that rebuilds a summary from the per-run JSONs, campaign by campaign
   (fitc10 `summarize.py`, `compare_variants.py`, `analytic.py`; weights `calib_fit.py`, `calib_retrim.py`,
   `calib_colsum.py`, `cv_eval.py`, `select_spice.py summary`, `eval_test.py summary`, `robustness.py summary`,
   `splits.py`, `report_tables.py`; energy `b1/b2/b4/b5_summary.py`, `report_tables.py`; host v2
   `summ_phases.py all`; host v2.1 `summ21.py all`) and checks that `docs/rev10_1_nominal.cir` rebuilds byte for byte;
2. compares every regenerated file with the committed one (`git status`; JSON files that differ only in formatting
   or key order are reported as such);
3. runs [`tools/check_results_index.py`](tools/check_results_index.py) against [`RESULTS_INDEX.md`](RESULTS_INDEX.md).

Expected: 23 steps, every step `ok`, "all regenerated files are byte-identical to the committed ones", "89/89 index
rows match" (65 campaign rows + 24 wrap-up rows `WU-…`), about 12 s. The weights steps need the pip packages of §1.
[`tools/check_concept.py`](tools/check_concept.py) checks every number in [`CONCEPT.md`](CONCEPT.md) against the index,
the specification and the prior-art notes (`python3 tools/check_concept.py`; expected "0 problems").

**Steps that need the waveforms or draw files (not included):** `phase3_c2slope.py` and `failure_devices.py phase3B_P`
(fitc10), `calib_mismatch.py` and `check_pairing.py` (weights), `b3_summary.py` and `b4_mu_explain.py` (energy). Their
committed summaries were built from the full data. To rebuild them, first regenerate the inputs they read by
re-running the corresponding phases (§6: fitc10 Phase 1, 3A and 3B-P; weights `runs.py K old`, `calib_stages.py sens`
and `mm`, A3 3B-V; energy `b3_mc.py cls`, `b4_aging.py`), then run the scripts from their `scripts/` folders. With the
original data, `b4_mu_explain.json` came out with the same content and a different key order (file-system `glob`
order); `check_pairing.py` covers whichever draw files are present (the committed summary covers 11 files).

The scripts write in place. Afterwards `git status` shows anything that came out different, and
`git checkout -- results docs` restores the committed files.

**Not rebuilt by this script** (their summaries come from simulations or long CPU searches; see §6): the stress audits
(`phase2_audit.json`, `A3_stress_*.json`, `c2_stress.json`; E2 is rebuilt from its per-run JSONs), Gate B / warm-start /
`mc_equiv` summaries, B5 short-run thresholds, host design constants, the A0 ceilings (≈ 22 min CPU), the A1 training
jobs and option-d screen, the A4 re-run, and the wrap-up summaries (`results/wrapup/REPORT.md` §7).

## 5. Smoke test: real SPICE runs against recorded outcomes

```bash
sh tools/smoke_test.sh
```

Five ngspice transients, run 4 at a time ([`tools/smoke_test.py`](tools/smoke_test.py)); each must reproduce the
outcome recorded in a committed file:

| Test | What is simulated | Must match |
|---|---|---|
| `lab81` | base design at the lab corner (`lab_vth085`), test sample #81, borrowed prior `t6L_x2_v085` (`build_A.py 81 t6L_x2_v085`) | [`results/fitc10_campaign/summary/smoke_lab_s81.json`](results/fitc10_campaign/summary/smoke_lab_s81.json): class 5, trip 903.80 µs, lock latency 14.90 µs, 134 TFTs |
| `v3_81` | `fitc10` Variant 3, #81, Variant 3 warm start, 2500 µs window | `results/fitc10_campaign/raw/v3/phase1/s81.json`: class 5, trip 1276.03 µs, lock latency 19.972 µs |
| `v3_31` | same, #31 (a near tie: runner-up gap 10.7 µs) | `results/fitc10_campaign/raw/v3/phase1/s31.json`: class 2, trips 1333.747 / 1345.871 µs, lock latency 19.617 µs |
| `v21_nom` | host protocol v2.1 at the nominal die (mode G), sample #1, start state and levels from `results/host_v21/raw/cal/v0650_m100/calibration.json` | `results/host_v2/raw/C3/C3_v0650_m100_learned_s01.json`: read {1}, race 1697.747 µs, read time 2265.447 µs |
| `v21_W51` | host protocol v2.1 at \|V_th\| 0.51 V (mode W), sample #1, the recorded E1 job | `results/host_v21/raw/E1/E1_v0510_m100_v21_s01.json`: read {1}, race 1390.058 µs, read time 1957.758 µs |

Match rule: same latched set, validity and failure label, and every time within 0.05 µs. Output: a table, then
`ALL MATCH: True` and the wall time; details in `/tmp/tortoise_smoke/smoke_summary.json` (`SMOKE_OUT` changes the
folder). Runtime about 3 min on 4 cores: in a fresh clone the five runs took 84, 132, 133, 103 and 89 s, 173 s wall
time in total. `sh tools/smoke_test.sh v3_81` runs a single test.

The `v21_nom` test compares against a host-v2 C3 run: the host-v2.1 study recorded no ordinary classification at
0.65 V (only the audited E2 runs), and mode G is v2 by definition (P2.2); the v2.1 nominal calibration start state,
levels and k are identical to v2's.

The canonical nominal netlist can also be rebuilt on its own: `python3 tools/gen_nominal_netlist.py --check`.

The dataset can be regenerated with [`data/generate_wound_data.py`](data/generate_wound_data.py)
(`python3 data/generate_wound_data.py --output /tmp/check.npz`). With numpy 2.5.3 the labels, groups, split indices
and metadata come out identical to `data/trace2_data.npz`, and the features agree to within 4e-15 (last-bit
floating-point differences from the numpy/libm build); every result in this repository was computed from the
committed `data/trace2_data.npz`.

## 6. Re-running a full campaign

Every campaign runner is **resumable: it skips any run whose per-run JSON already exists.** To re-run a phase, move
its raw folder aside first (in your clone), e.g. `mv results/fitc10_campaign/raw/v3/phase1 /tmp/phase1_committed`,
then run the commands below and compare the new per-run JSONs or summaries with the committed ones (`git diff`).
Re-running a phase also writes its waveforms (`*.csv.gz`), simulated netlists (`*.cir.gz`) and Monte Carlo draws
(`*_draws.json`) next to the per-run JSONs: this is how the data not included in this repository are regenerated.
The campaign `run_*.sh` drivers record the order in which the phases were run; some assume paths of the original
machine, so **use the per-phase commands below instead of the drivers.** All commands assume §3 has been run. Times
are from the campaigns' own run logs (4-core VMs, ngspice-42).

## 7. Notes
- Each campaign's `DECISIONS.md` fixes its protocol before its runs and records dated deviations. Re-running a campaign reproduces its numbers only with the same ngspice version and the same inputs.
- Warm-start chains start from the borrowed lab prior `rev10/sim/circuits/t6L_x2_v085.{dat,cols}`.
- Scripts import each other read-only across campaign folders (host v2.1 → host v2 → energy → fitc10 → `rev10`); do
  not move the folders.
